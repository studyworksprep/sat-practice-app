# SAT import comparison

**Living** — last verified 2026-09-15.

Admins open **Questions → Import questions** (`/admin/questions/import`). The screen compares imports and can apply an individually confirmed presentation replacement to a live, published question. It also inserts reviewed new questions into the regular bank or restricted supplemental sets, and holds unanswered questions as unpublished drafts. Every server action and the page require the admin role; all mutation actions reject demo accounts.

Upload a Mathpix MMD ZIP (including figures) or an MMD file, optionally paired with a PDF and metadata. The supported first format is the College Board export with `Question ID` headings, `Question`, optional `Answer` choices, `Correct Answer`, and `Rationale`. Metadata is a JSON array in JSON/plain text or a TextEdit RTF wrapper. Numbered exports also support `## Question 1` or `\\section*{Question 1}` headings, A–D choices on separate lines, and optional Correct Answer / Explanation headings. Content-derived IDs prevent page numbering from becoming a source identifier. Metadata may supply `correct_answer` as a string or string array when the export lacks a key; conflicting keys raise a review warning. Other metadata layouts and OCR providers are not yet supported. A PDF alone cannot be processed by this screen.

Questions group by ID, not page count: continued explanations stay attached to their question. Headers/difficulty graphics are removed, while body tables and referenced figures are retained. Supported math is rendered through the shared math renderer, then displayed through `QuestionRenderer` just like bank questions. Standalone imported equations use compact inline math inside explicitly centered paragraphs, so alignment survives sanitization and fraction sizes match the bank convention. Equation blocks inside choices are left-aligned on separate lines. Body tables are emitted outside paragraph wrappers. Simple table cells contain inline content without paragraph margins, with centered values and scoped column headers. Correct answers and explanations stay separate from prompt content. Broken markup, missing figures, repeated IDs, and invalid choices reject the batch with a message.

Uploads compare identifiers (`questionId`, `external_id`, `ibn`) against `questions_v2.source_id` and `source_external_id` in the app's configured database. Multiple matches require selection. Live comparisons also check normalized visible prompt text across both pools. This is conservative candidate detection, not semantic equivalence: differently encoded math/images may evade it, and the same stem with different figures may be flagged for review. New inserts recheck duplicates in a transaction; all inserts through the import RPC share an advisory lock. Deleted, broken, and unpublished matches are shown with status warnings. Question comparisons do not query student attempts. Set management reads account email and grant information for admin access management.

The **Load local math pilot** button reads fixed files under `content/import/pilot/`, including `analysis/bank-comparison.json`, a read-only production snapshot for the ten sample questions. This lets the pilot work against a development bank that lacks these records. The snapshot label and capture date appear on screen and in review exports. It is never treated as a live query. The button reports a file-unavailable message on installations without the local fixtures; normal uploads still work. Pilot files are gitignored and excluded from this change. The local-pilot button is hidden in production, and its server action rejects production calls. Use the upload form for live-bank comparisons.

Each question has existing/imported previews, a reveal toggle, answer/difficulty/score-band comparison, and source PDF access. An imported rendering preference does not approve metadata or answer changes. Uploaded PDFs remain in the browser as temporary object URLs. MMD and metadata reach the authenticated server for parsing; figures are embedded in the returned preview. Nothing is uploaded to Storage.

Review preferences remain in component state and are lost on reload or a new batch. **Export review choices** downloads a JSON review log containing matched IDs, existing update timestamps, warnings, and preferences. It is not an import/apply payload. Exports also record successful applies during the current session; there is no restore endpoint.

Limits: 100 questions, 8 MB compressed export, 1 MB metadata/MMD text, 12 MB expanded archive, 500 archive entries, and 25 MB local PDF. ZIP processing rejects traversal paths and oversized entries. Imported HTML is escaped and previews use the shared sanitizer.

Validation: parser/archive unit tests cover page continuations, multiple accepted numeric strings, legacy IDs, ambiguous matches, table retention, unsafe HTML, missing figures, duplicate IDs, archive limits, and RTF metadata. An admin E2E test covers an unmatched question and review export; the optional pilot-upload test uses `E2E_IMPORT_PILOT=1`. Replacement protection tests cover signed review tampering, expiry, actor binding, and option identity preservation. Supplemental insertion/access tests are opt-in with `E2E_IMPORT_SETS=1`.

## Applying a replacement

**Prefer imported** records a preference. It then reveals a separate confirmation and **Apply imported presentation** button for that individual match. Admins must confirm that text, options, figures, and explanation have identical meaning; identifier matching does not establish semantic equivalence. The action updates stem, supplied rationale, choice markup, their rendered caches, and editor attribution on the same row. Option labels, order, IDs, and other option properties are retained. Answers, difficulty, taxonomy, pool, publication status, and student records are never included in the update. Missing imported rationales retain the bank rationale. Embedded figures are persisted directly in HTML as data URLs in this first release; they do not depend on local files or temporary browser URLs.

Only live comparisons issue signed, actor-bound, two-hour review tokens. Use `IMPORT_REVIEW_SECRET` as a stable server-only signing key; the existing server-only `SUPABASE_SERVICE_ROLE_KEY` is the fallback. Missing signing configuration disables applying. Tokens bind the proposed markup, target ID, and original update timestamp. The server checks the signature and admin identity before an atomic conditional update. An intervening edit or repeated submission cannot overwrite the newer record; compare again after any uncertain result. Snapshot reviews cannot issue tokens.

Published, active questions with matching answer type, answer strings, and unambiguous option sets are eligible. Separate stimulus passages and multiple-answer MCQs require separate editing. Metadata differences can remain because metadata is preserved. The existing database trigger saves prior content to `question_content_history` atomically with the edit; this is edit history, not a new question record or student-facing version. Apply is per question, with visible success/failure, and refreshing clears local receipts. Replacement itself uses the existing schema; the expanded importer requires the supplemental migrations below.

Development integration verified on 2026-09-14: the opt-in `question-import-replacement.admin.spec.ts` uses three uniquely identified, opt-in-pool copies of the equation, graph/MCQ, and table pilot questions. It drives the real login, upload, confirmation, and apply UI against the allowlisted development project. It checks every non-presentation column, stable option IDs, a synthetic practice attempt, prior-content history, and rejection of an intervening edit before re-review. Cleanup removes its question UUIDs, attempt, and cascading history. Run with `E2E_IMPORT_REPLACE=1 E2E_BASE_URL=http://127.0.0.1:3000 npx playwright test tests/e2e/question-import-replacement.admin.spec.ts --project=admin --no-deps --workers=1` while the local server uses the development database. It uses the seeded development admin and public API key, not a service-role key. Production is never a permitted test target.

## New questions and supplemental access

Create a named supplemental set with source, optional date and notes, or choose an existing set. Unmatched questions offer **Supplemental practice set** (default) and **Regular question bank** destinations. Regular imports require domain name, skill name and difficulty; supplemental imports preserve unknown fields as NULL. Each insertion requires review confirmation. Publication additionally requires a usable numeric/fraction or A–D answer key and the admin’s verification. Missing or malformed answers remain unpublished drafts. Use the existing question editor to fix a draft, then refresh the set’s draft list and publish after verification. The list shows the 200 most recent supplemental drafts; older drafts remain in the question bank.

Supplemental questions and their batches remain opt-in. Staff can review them; students need an explicit `question_batch_access` grant AND a published, active question. Admins grant/revoke access by account email. Restrictive RLS protects direct ID reads and the student launcher’s security-invoker batch view; anonymous reads of supplemental sets are denied. Grants do not bypass subscription requirements. Automatic unlocking based on completion is not implemented. Existing attempts are retained when access is revoked, but question content is no longer readable to that student.

New imports use signed, actor-bound insertion tokens with a fixed question UUID for retry idempotency. They never use a replacement token. A repeated insertion returns the existing record and its actual publication state, without overwriting it. Source IDs and conservative prompt-text duplicate checks span both pools, including deleted/unpublished records; a possible duplicate must go through comparison instead of insertion. This does not replace visual duplicate review.
